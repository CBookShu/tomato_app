# GitHub 同步与绑定设计文档

## 概述

本次设计补全 Tomato App 的 GitHub 同步与绑定流程。用户先准备一个完整的 GitHub 仓库 URL，App 在设置页中完成授权、绑定、远程配置，并把本地目录作为一份真正的 Git 仓库来使用。

同步不再被抽象成一套自定义协议，而是尽量回到标准 Git 行为：

- 本地目录始终是仓库
- 远程绑定只是配置 `origin`
- 同步就是 Git 的 `fetch` / `pull` / `push`
- 冲突时先保住本地数据，再交给用户手动处理

## 目标

- 支持用户粘贴完整 GitHub 仓库 URL 作为同步目标
- 点击连接后自动完成 GitHub OAuth 授权
- 授权成功后保存 token 与仓库绑定信息
- 本地目录始终保持为 Git 仓库
- 支持空仓库，首次绑定时由后台自动初始化并推送首次提交
- 绑定成功后明确显示已登录、已绑定、最近同步等状态
- 支持解绑，解绑后回到未配置状态
- 遇到 URL 无效、登录失败、GitHub 配置缺失、网络失败时给出明确错误
- 遇到远端已有提交、双向修改或拉取冲突时，先保留本地数据，不自动丢弃任何本地内容

## 非目标

- 不新增“创建 GitHub 仓库”的向导
- 不在 UI 中单独暴露“空仓库初始化”步骤
- 不实现多仓库切换
- 不实现团队协作或多用户权限
- 不实现可视化 merge editor
- 不重做整个同步引擎的数据模型

## 用户流程

```mermaid
flowchart TD
  A[设置页打开数据同步卡片] --> B[用户粘贴完整 GitHub 仓库 URL]
  B --> C[点击 验证并连接]
  C --> D{URL 是否合法}
  D -- 否 --> E[显示输入错误]
  D -- 是 --> F[检查 GitHub 配置与登录状态]
  F --> G{是否需要 OAuth}
  G -- 需要 --> H[打开 GitHub 授权]
  G -- 已有凭证 --> I[继续绑定]
  H --> I
  I --> J[保存 token 与仓库 URL]
  J --> K[配置 origin 并确保本地是 Git 仓库]
  K --> L{远端是否为空仓库}
  L -- 是 --> M[提交本地初始快照并 push]
  L -- 否 --> N[fetch 远端并执行首次同步]
  M --> O[显示已绑定状态]
  N --> P{是否发生冲突}
  P -- 否 --> O
  P -- 是 --> Q[创建本地备份分支并中止同步]
  Q --> R[显示冲突提示给用户手动处理]
  O --> S[用户可手动同步]
  O --> T[用户可解绑]
  R --> T
  T --> U[清除 token 与仓库绑定]
  U --> V[回到未绑定状态]
```

## UI 设计

### 位置

数据同步仍然放在设置页中，但采用一个高可见度的内联卡片，不再依赖用户先发现隐藏入口。卡片默认显示以下内容：

- 标题：`数据同步`
- 说明文案：先填写完整仓库 URL，App 会自动完成授权和绑定
- 仓库地址输入框
- `验证并连接` 按钮
- 当前状态标签
- `解绑` 按钮
- 错误提示区

### 绑定态

绑定成功后，卡片显示：

- `已登录 GitHub`
- `仓库已绑定`
- 最近同步时间
- `立即同步` 按钮
- `解绑` 按钮
- 如果当前处于冲突态，显示备份分支名称和手动处理提示

### 未绑定态

未绑定时，卡片应当让用户一眼知道下一步是什么：

- 输入框始终可见
- 连接按钮始终可见
- 说明文字直接提示支持空仓库
- 不要求用户先展开折叠区或跳转到向导

### 错误态

错误信息应优先展示在同步卡片内部，而不是仅依赖控制台日志。错误文案要区分以下几类：

- 仓库 URL 格式不合法
- GitHub OAuth 配置缺失
- OAuth 过程取消或失败
- 网络失败或 GitHub 返回错误
- 后台初始化失败
- 本地 Git 仓库初始化失败
- 远端 fetch / pull / push 失败

## 数据与状态

### 新增绑定信息

同步能力当前只保存 token 和运行时状态，还需要补充仓库绑定信息。设计上建议新增一份持久化同步配置，至少包含：

- `repositoryUrl`
- `repositoryOwner`
- `repositoryName`
- `boundAt`
- `lastSyncTime`
- `remoteName`
- `localBranch`

其中 `repositoryOwner` 和 `repositoryName` 可以在用户输入完整 URL 后解析得到，便于后端初始化仓库时直接使用。

### 状态机

同步状态需要区分“登录状态”、“仓库绑定状态”和“Git 同步状态”：

- `未绑定`
- `绑定中`
- `已绑定`
- `同步中`
- `有冲突`
- `失败`

这几个维度不要混成一个状态字符串，否则 UI 很容易出现“已登录但未绑定”或“已绑定但 token 丢失”时无法表达的情况。

## 同步模型

### 本地仓库

本地数据目录始终被视为一个独立的 Git 仓库。设计上不再区分“本地数据”和“本地仓库”两个概念，它们是同一件事。

如果本地目录还不是仓库，App 在首次绑定或同步前自动执行初始化：

- 创建 `.git`
- 写入 Git 配置
- 绑定当前工作分支

### 远程绑定

远程绑定只意味着把用户提供的 GitHub 仓库 URL 设置为 `origin`。设计上不引入额外的同步服务器或中间层。

### 认证

OAuth 只负责拿到可用于 GitHub 仓库访问的凭证。后续 push / pull 仍然是标准 Git 操作，只是这些命令会使用保存下来的 GitHub 凭证。

## 首次同步

### 空仓库

如果远端仓库是空仓库，App 的行为如下：

1. 确保本地仓库已经初始化
2. 提交本地当前快照
3. 添加或更新 `origin`
4. 推送到远端默认分支
5. 标记为已绑定并可继续同步

### 远端已有数据

如果远端仓库已有提交，App 采用 Git 原生拉取合并策略：

1. 先提交本地未保存的变更
2. 再执行 `fetch`
3. 再执行 Git 原生 `pull`
4. 如果没有冲突，直接进入已绑定状态
5. 如果发生冲突，进入冲突保护流程

这里不做“远端优先覆盖本地”或“本地优先覆盖远端”的自定义协议判断。Git 已经给出了标准合并结果，App 只负责在冲突时保护本地数据并把控制权交给用户。

## 后端流程

### 连接流程

1. Renderer 发送绑定请求，携带完整仓库 URL
2. Main 进程校验 URL 结构
3. Main 进程检查 GitHub token 是否存在
4. 如果没有 token，则启动 OAuth
5. OAuth 成功后保存 token
6. 解析仓库 owner/name 并写入绑定配置
7. 确保本地目录已经是 Git 仓库
8. 配置或更新 `origin`
9. 如果远端是空仓库，则自动完成首次提交与 push
10. 如果远端已有数据，则执行 Git 原生 pull / merge
11. 如果发生冲突，创建本地备份分支并停止同步
12. 返回绑定结果给 Renderer

### 解绑流程

1. 用户点击解绑
2. Main 进程删除 token
3. Main 进程清除仓库绑定配置
4. 清空同步运行时状态
5. Renderer 回到未绑定态

### 空仓库处理

空仓库无需在 UI 中单独展示。后台逻辑负责判断仓库是否没有提交历史，然后自动执行首次初始化动作。这里的产品含义是：

- 用户只需要提供一个新建好的空仓库 URL
- App 会在后台把本地数据做成第一次可同步的 Git 提交
- 用户不需要理解“初始化仓库”这个技术步骤

### 冲突处理

如果 `pull` 或合并过程中发生冲突，App 采用以下保护策略：

1. 中止当前 Git 操作
2. 创建本地备份分支，例如 `local-backup-2026-05-13T12-30-00`
3. 保留当前本地提交和工作区数据
4. 将同步状态置为 `有冲突`
5. 在 UI 中提示用户手动处理

冲突态下，App 不会自动 `reset` 到远端，也不会自动丢弃本地改动。用户如果希望直接回到远端版本，需要显式选择回滚操作。

## 失败与恢复

- 如果 URL 不是 `https://github.com/<owner>/<repo>` 形式，直接阻止连接
- 如果 GitHub OAuth 环境变量缺失，按钮点击后立即报错
- 如果 OAuth 打开了但用户取消，返回可读错误
- 如果仓库地址对应的远端不可用，提示用户检查仓库地址或权限
- 如果解绑时 token 删除失败，保留错误状态但不破坏现有绑定信息，避免半解绑
- 如果 pull 过程中出现冲突，先创建备份分支再停止同步
- 如果 remote 有历史数据，首次绑定不会覆盖远端历史

## 测试策略

### 单元测试

- 校验 GitHub 仓库 URL 解析规则
- 校验绑定状态在登录、解绑、错误、同步中的转换
- 校验空仓库初始化路径在成功与失败时的返回值
- 校验首次绑定时 remote 绑定与本地仓库初始化顺序
- 校验冲突时会创建备份分支而不是直接丢弃本地内容

### 集成测试

- 通过 IPC 测试连接请求能正确进入 main 进程
- 通过 store 测试绑定后状态会更新为已绑定
- 通过解绑测试状态能完全重置
- 通过集成测试验证远端已有数据时首次同步不会覆盖本地仓库
- 通过集成测试验证冲突后会进入冲突态并保留备份分支名称

### E2E 测试

- 打开设置页时可直接看到同步卡片
- 输入完整仓库 URL 后能触发连接
- 连接成功后显示已绑定状态
- 解绑后回到未绑定态
- 如果 GitHub 配置缺失，UI 会显示错误而不是无响应
- 当远端存在数据时，首次绑定后页面能进入已同步或冲突状态
- 当发生冲突时，页面会显示备份分支和手动处理提示

## 验收标准

- 用户可以在设置页直接看到同步入口
- 用户可以粘贴完整 GitHub 仓库 URL 并完成绑定
- 空仓库可以作为同步目标并在后台自动初始化
- 远端已有历史数据时，App 仍然以 Git 原生同步方式接管，不会自定义覆盖远端
- 绑定成功后 UI 明确展示登录与绑定状态
- 用户可以解绑，解绑后同步状态被清空
- 冲突发生时，本地数据被保留并生成备份分支
- 所有失败场景都有可读错误提示

## 备注

本设计保留当前同步系统的总体方向，只把它明确成标准 Git 工作流。下一步实现时，优先把仓库绑定状态、token 状态和 Git 同步状态分开建模，再逐步接入 UI 与 IPC。
